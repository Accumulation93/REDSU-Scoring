# 审核印章授权

## 管理入口与 UI

管理端审核的印章页，每枚印章独立提供“配置可用人”。新增印章保存成功后直接进入授权选择；取消表示暂不授权，列表明确显示暂无人可用。再次打开恢复已保存岗位，可多选、取消单项、确认清空。加载失败保留已有内容并提供重试，不得显示成无授权。

使用全仓 `personnel-picker` 的 `assignment` 模式，复用 UI Kit 的白色窗口、固定底栏和三档设备令牌。按部门、身份类别、职能组筛选时必须由同一岗位同时满足；最终选择键为 `assignmentId`，不按类别整体授权、不合并同人多岗，不返回或展示学号。

## 组织与权限

印章外卡只显示名称、缩略图、可用岗位数量及必要的待配置提示，不展示可用人员姓名和岗位名单。具体授权仅在“配置可用人”内展开核对。外卡使用纵向布局，操作栏独立放在摘要下方，禁止把 `width:100%` 的操作行和摘要挤在同一横向行。

- 印章和授权始终属于一个组织。跨组织不共享图片记录或授权，另一组织必须重新添加并授权；同名印章也不互通。
- 只有当前组织 `audit.stamps` 管理权限可读取候选或保存授权，不要求附带人事资料管理权限。
- `listStampCandidates` 返回当前组织在职自然人的有效岗位及姓名、岗位分类，不返回学号。
- `saveStampGrants` 接受 `{ stampId, assignmentIds: string[] }`，最多 1000 项、去重，空数组表示撤销全部。任意无效、跨组织或失效岗位导致整批拒绝。
- `listMyStamps` 与实际盖章共用 `stampAssignmentGrant.getAuthorizedStamps`，检查组织、自然人、具体岗位及有效成员关系。盖章事务中锁定授权与原图，客户端图像不能替换服务端原图。
- 授权撤销、岗位停用或离任立即影响后续用章，不修改已经完成的签署历史。人员永久删除预检包含印章授权，删除时清理所属组织授权。
- 自然人合并导致岗位所属人员变化时，旧授权不自动转给合并目标；管理员必须重新确认，避免合并扩大用章权限。

## 数据与兼容

时间戳迁移新增 `stamp_assignment_grants`。旧 `identity_stamp_assignments` 保留以供管理员识别，但不再作为授权依据；不把类别自动展开成所有人员。旧 `saveStampAssignments` 返回明确退役提示，管理员在新入口重新确认具体岗位。
