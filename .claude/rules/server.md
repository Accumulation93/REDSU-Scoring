# Express 后端规则

本文件描述当前服务端边界。完整数据库事实以 `server/db/init.sql` 和按文件名顺序已执行的 `server/db/deploy/*.sql` 为准；不要以历史 NoSQL 导出、旧路由清单或固定文件行数推断当前结构。

## 1. 运行时与目录

- `server/src/index.js` 启动 Express HTTP 服务，仅监听 `127.0.0.1:${PORT}`；生产 HTTPS 由 Nginx 反向代理终止。
- `server/src/core/` 放认证、组织、人事、管理员、文件解析等跨模块核心路由和模型。
- `server/src/modules/scoring/`、`server/src/modules/audit/`、`server/src/modules/venue/` 放模块专属路由、模型和领域逻辑。
- `server/src/config/`、`middleware/`、`utils/`、`locales/` 分别承担配置、请求边界、基础工具和用户可见语言资源。

## 2. 中间件顺序

以 `server/src/index.js` 的注册顺序为准：请求上下文与响应保护 → 请求超时 → Morgan/Helmet/CORS → 客户端版本 → 进程内快速限流与高风险共享限流 → `/api/ping`、带短缓存的 `/api/health` → 公开认证入口的小体积请求解析 → 认证 → 上传账号共享限流 → 受保护请求体解析与复杂度限制 → 组织上下文 → 管理员权限 → 受保护健康接口和业务路由 → 404 → 错误处理。修改顺序时必须同步检查公共入口、组织隔离和错误响应。

## 3. 认证与组织上下文

- 公开入口包括 `/api/ping`、`/api/health`、旧版 `userLogin/adminLogin` 以及统一认证的微信会话、工作上下文声明、口令会话和恢复入口；具体集合以 `server/src/middleware/auth.js` 为事实来源。
- 除公开入口外，所有请求必须携带有效 JWT。统一身份令牌还必须通过服务端会话、账号 token 版本和组织/工作上下文校验；缺少或失效令牌返回 401，不再把未认证请求放行给业务路由。
- 统一令牌中的服务端组织/工作上下文是授权来源；旧客户端的 `X-Active-Org`、`X-Role` 仅作兼容输入，不能绕过服务端上下文。
- 所有组织域查询必须验证当前 `org_id`；切换组织/工作上下文时作废旧请求和缓存，不能让旧上下文的迟到响应覆盖当前页面。

## 4. 响应契约

- 成功接口沿用既有业务契约：常见形式为 `{ status: 'success', ... }` 或 `{ status: 'success', data: {...} }`；修改接口前必须读取调用方和现有路由，不能擅自把一种形式批量改成另一种。
- 登录/统一认证响应使用约定的 `login_success`、`need_bind`、`success`、`auth_failed` 等状态及其既有字段；字段名、状态值和错误语义必须向后兼容。
- 统一认证只依据微信绑定、账号状态和有效工作角色放行。设备安装标识、设备摘要、平台和型号不得用于登录校验、会话互斥或续期校验；同一账号允许在多台设备保持相互独立的有效会话。设备信息如需保留，只能作为可选审计展示元数据，缺失或变化不得影响认证结果。
- `res.json` 会补充 `requestId` 并通过公共文案保护层处理用户可见信息。内部日志可以记录诊断信息，但不得把内部 ID、堆栈或数据库术语直接返回客户端。
- 通用 `status: error/internal_error` 必须由公共文案保护层失败关闭为统一提示，禁止透传捕获到的 `error.message`、驱动消息、绝对路径或第三方响应。需要精确反馈的可预期业务失败使用明确状态和 locale 文案。

## 5. 数据库与安全

- SQL 必须参数化并放在 Model/领域服务层；路由只做输入校验、授权和响应编排。
- 组织域数据必须带组织边界；跨组织、全局超级管理员、通知 Worker 等例外必须有明确代码路径和测试，不得用缺少 `WHERE org_id` 的宽查询代替授权。
- 常规业务主键使用 `VARCHAR(64)` 和 `generateId()`；部署元数据表 `schema_migrations.name VARCHAR(255)` 是迁移账本的明确例外，不得把该例外扩散到业务表。
- 连接池、事务和 `SET SESSION max_execution_time` 使用 `server/src/config/db.js` 的现行实现；事务失败必须回滚并释放连接。
- 禁止在业务 SQL 中拼接用户输入、动态表名或未审计的排序字段；动态标识符只能来自显式白名单。
- 逗号分隔或 JSON 中保存的字典 ID 集合必须按元素校验组织归属，并用组织级字典锁同时覆盖“检查后写入”和“检查后删除”；禁止把集合列当单值外键或将整串值直接 JOIN 字典表。若未来规范化，必须保留原条件组的 OR 语义并对比迁移前后候选集合。
- 认证与必要的廉价请求边界必须先于大体积 JSON/表单解析；公开认证入口只开放其所需的小体积解析器。不得让未认证请求先占用通用大请求体解析、文件解码或数据库重查询资源。
- `/api/health` 等公开探针必须采用短期缓存和受控限流，不能让每次匿名请求直接触发数据库查询。PM2 多进程下的登录、口令、恢复、上传等高风险限流必须使用数据库或等价共享存储做原子计数；共享存储异常时高风险入口失败关闭，普通业务不得被无差别拖垮。
- 临时文件上传必须同时实施单文件、单账号累计、全局累计和过期清理限制；配额检查与登记需跨进程原子化。磁盘路径只保存服务端生成的不可猜测标识，下载/预览/读取除组织与资源归属校验外还必须校验细粒度权限，禁止“是组织管理员即可读取全部附件”。
- 口令最小长度是服务端强制安全下限，系统配置只能提高、不能降低；新增认证或凭据入口必须复用同一策略和限流。
- 任何已跟踪源码、脚本、测试、示例和日志都不得保存真实凭据；数据库脚本必须从环境变量读取并缺失即失败。发布门禁必须扫描当前跟踪文件中的凭据字面量；历史凭据一经发现按已泄露处理并先轮换失效，未经明确授权不得强推改写共享 Git 历史。
- 生产 `JWT_SECRET` 与身份加密、附件令牌、PDF 私钥信封加密等用途密钥必须独立，且每个密钥至少 32 字节随机熵；禁止把 JWT 密钥静默复用于身份加密或私钥加密。密钥强度、用途分离和必要版本必须在启动及部署预检中失败关闭，任何日志和响应不得输出密钥或密文解密材料。
- PDF/签章私钥不得以明文写入业务数据库或备份；只允许保存带算法与密钥版本的认证加密密文，主密钥必须位于数据库之外。旧明文迁移必须幂等、可核验并在迁移成功后清除明文；读取兼容只能作为受控过渡，不得让新写继续落明文。
- 备份、附件、临时上传和包含凭据的共享目录统一采用进程 `umask 077`、目录 `0700`、文件 `0600`，创建后再次校验权限。上传从临时区挂接到正式目录必须与数据库事实协调回滚；文件名按 Unicode 字符和数据库列上限校验，并定期核对“临时配额—数据库记录—磁盘文件”三方一致性，只能清理达到安全年龄且无数据库引用的孤儿。
- 人员永久删除执行必须要求幂等请求 ID，并在事务中获取删除屏障、行锁、版本校验；所有可能新增该人员业务事实、待审资料或签名原图的入口必须先获取同一屏障。规则移除指定人员后的候选复核必须取“规则条件 ∩ 在职成员 ∩ 有效岗位”，不得只检查字符串 ID 是否残留。

## 6. 领域边界

- 评分：`modules/scoring`，负责活动、模板、规则、评分提交、结果和公示。
- 审核：`modules/audit`，负责审核流程、审批、签名/验签、通知、附件和 read cursor；附件必须写入共享持久目录，不得写入 release。
- 场地：`modules/venue`，负责场地、开放/截止窗口、活动占用、预约、审批流、审批历史和详情。
- 统一认证、人事、组织、权限、系统和文件表格能力位于 `core`，不得在模块内复制第二套认证或组织上下文实现。

## 7. 人事领域与授权边界

- 自然人是跨组织实体；账号是自然人的全局账号；组织成员关系表示自然人在某组织中的在职关系；岗位是该关系下的任职记录。组织成员可以在职但没有岗位。
- 本人资料读取和保存必须使用认证中间件确认的账号自然人及当前组织成员关系，临时口令会话不得依赖 `user_info.openid` 或永久微信绑定；禁止按当前微信、姓名、学号或客户端人员 ID 重新确定本人。保存须在事务内以该自然人、组织及成员档案获取删除屏障。管理资料接口复用已认证管理角色与细权限，禁止按旧 `admin_info.openid` 二次认证。
- `membership_assignments` 是岗位唯一事实来源。岗位固定为岗位性质、部门、身份类别和可选职能组；禁止保存或判读自由文本岗位名称。展示名由“身份类别 · 部门 · 职能组”生成；非空职能组的所属部门必须与岗位部门一致。岗位性质缺失或不属于受支持枚举时必须拒绝保存，禁止静默回落为本会岗位。
- 新接口和内部变量统一使用 `contextId`（工作上下文）、`assignmentId`（岗位）、`identityCategoryId/Name`（身份类别）、`assignmentNature` 和 `assignmentLabel`。旧 `identityId` 只能作为兼容输入/输出映射，不得参与新判权。
- 审核、场地和评分动作只使用当前 `assignmentId` 授权；不得从 `hr_info.department_id/identity_id/work_group_id` 或任意兼容岗位推导权限。无岗位成员只能使用不依赖岗位规则的组织公共能力。
- 发起、候选、审批、场地和评分操作必须保存不可变的组织、`contextId`、`assignmentId` 及岗位性质/部门/身份类别/职能组快照；历史查询优先读取操作时快照，后续调岗不能改变历史含义。
- 补充资料状态与完整度分别计算；只要存在待审提交，状态就是 `pending`。人员维护者只能维护已生效资料，资料审核员只能比较和审核待审值；驳回原因必填，资料、全局生效值和审核历史必须在同一事务中写入。
- 成员退出动作是“离开当前组织”：停用成员关系和全部岗位，但保留自然人、全局账号及历史。冻结、解绑、初始化或修改登录口令、重置跨组织账号必须校验 `auth.accounts.global_manage`，组织管理员权限不得隐式扩大为全局账号治理权。在职成员尚无账号时允许在事务中按自然人创建唯一 `verified` 账号；已有账号必须复用且不得修改冻结状态或撤销既有会话。
- 未绑定账号首次口令认证必须在口令验证成功后才交换微信 code 并补充绑定；已有账号绑定不得替换，微信已绑定其他账号时必须拒绝。绑定成功并同步兼容映射后才能建立依赖微信身份的统一会话；已绑定账号继续兼容未传 code 的旧客户端。
- 人事成员目录必须一次返回当前权限范围内的全部在职与已离开成员，前端本地筛选；离任成员详情可读取离任前岗位。岗位性质、部门、身份类别和职能组组合筛选必须落在同一条岗位元组，不得用独立 `EXISTS` 或扁平数组跨岗位拼接命中。
- 永久删除组织成员或自然人必须先做全引用预检，并在执行时复核版本。审核、场地、评分、资料审核历史等业务事实一律阻断；允许清理的未执行规则、授权、会话、签名模板和认证数据在事务中处理，清理后零候选的模板/规则必须停用。组织删除保留其他组织和全局账号；自然人删除仅限超级管理员，禁止删除当前操作者或最后有效超级管理员，并只保留去标识审计。组织成员删除也可能移除 `admin_grants`，因此两种永久删除范围都必须先在事务中获取同一全局超级管理员治理锁，再锁定目标人员并复核“最后有效超级管理员”；禁止只保护自然人范围。所有可能新增人员业务事实或签名原图的写入必须先获取人员删除屏障，禁止与永久删除形成 TOCTOU。
- 删除部门、身份类别或职能组前必须检查岗位、审核、场地、评分、印章、发布权限、快照和历史等全部引用；任何引用都直接阻止删除并返回分类数量。不得自动替换，也不得以“停用”绕过引用完整性。

## 8. 迁移与发布

- 生产只使用 `server/db/deploy/` 中的时间戳幂等迁移和 `schema_migrations` 账本；旧 `migrate.sh/migrate.bat` 只可作为历史兼容工具，不能声称覆盖当前全部迁移，也不得直接用于生产。
- 有数据库结构或数据变更时新增迁移，不修改已执行迁移；纯前端、文档和样式改动不伪造迁移。
- 修改后执行与范围匹配的测试、权限/租户审计、迁移预检和 `git diff --check`。推送后由 GitHub Actions 先通过 `audit-and-test`，再执行部署；部署后核对完整 SHA、release/current、PM2 进程、迁移账本和本地/公网健康接口。
- CI 的 `GITHUB_TOKEN` 权限默认固定为 `contents: read`，第三方 Action 固定到经过核对的完整提交 SHA，并关闭 checkout 凭据持久化。部署锁必须在任何远端文件、Git、日志或软链接写入前取得；锁竞争失败的任务不得留下部分状态。

### 8.1 绝对时间与历史校正

- 数据库连接和会话时区统一为 UTC，绝对时间统一保存为 UTC `DATETIME(3)`；`system_config.timezone` 只作为显示时区偏移。禁止继续手工拼接 `toISOString().slice(...).replace(...)` 写数据库。
- 服务端绝对时间统一返回 ISO UTC，并在登录、上下文目录和系统配置接口返回 `systemTimezoneOffset` 与配置版本。`YYYY-MM-DD`、`HH:mm`、时长、提前量和周期规则不是绝对时间，不得转换。
- 历史迁移按已知写入来源逐表逐字段分类：数据库本地墙上时间转 UTC，代码已写 UTC 的记录不重复移动；无法确认来源的记录写入迁移审计，禁止猜测。迁移前必须输出字段、来源、数量和样本，存在未分类的用户可见时间字段时停止发布。
- 可证明由旧 UTC+8 连接与 `CURRENT_TIMESTAMP` 生成的墙上时间字段统一减 480 分钟；混合来源字段只按主键游标分批物化逐记录待核对账本，不自动平移。逐记录账本必须保存可映射业务记录标识，响应层按“记录标识 + 原始绝对时间”附加字段级 `*ReviewStatus`；存在未解决记录时 cutover 只能是 `review_pending`，且 `presentationMappedReviewCount` 必须等于未解决数，只有未解决数为零才可标记 `verified`。迁移账本与 cutover 独立；历史关系回填必须显式保护 `ON UPDATE` 事实时间。
- 待核对时间映射必须使用“表 + 字段 + 业务主键 + 原始值”的精确键，禁止仅按值或模糊 ID 关联。遍历达到安全上限时必须明确失败并阻止发布，禁止静默截断；物化结果只能报告实际写入并可由展示层精确命中的数量，禁止用未解决总数伪造映射成功数。

### 8.2 历史业务事实不可变

- 审核轮次、签名、场地审批与岗位快照是不可变业务事实。评分题目和规则解释必须保持记录发生时的依据，但评分答案只保留当前结果；重新评分在同一事务内校验状态、加锁、覆盖答案并递增并发版本号，不保存旧评分副本，也不得按当前配置重算原有题目。
- 新轮次使用新记录并把旧步骤标记为不可变历史状态；待审重提交必须创建新的首个待处理步骤。旧模板或快照不足时明确失败关闭或标记历史信息缺失，不得借读取动作“修复”历史。
- 历史评分必须使用提交时模板、题目、规则和岗位快照。当前模板签名变化不得在读取时删除答案、改写签名或重新解释历史总分；确需数据修复只能通过幂等迁移与审计完成。

## 9. 用户可见文案

- API 响应、公开错误、通知、待办和导出标题只能来自 `server/src/locales/zh-CN/**`；业务代码通过语言资源和变量参数生成动态句子。
- 状态码、路由、权限键、SQL、数据库值和内部日志不是语言资源，不得为了通过审计而错误移入 locale。
- 完成服务端修改必须运行 `node scripts/user-visible-copy-audit.js --localization-prefix=server/src/ --strict-localization`，并按任务要求运行 `--strict-guidance`。
