# CLAUDE.md — 审核模块 (audit)

> 模块专属规范。通用规范见根目录 `CLAUDE.md` 和 `.claude/rules/miniprogram.md`。

## 1. 模块结构

```
audit/
├── styles/blue-polish.wxss
├── components/signaturePad/   # 普通 View 实时笔迹 + 隐藏 Canvas 1:1 导出器
└── pages/

    ├── pendingApprovals/       # 待审批列表（30s 轮询）

    └── verification/           # 哈希链验证
```

## 2. submissionDetail 核心架构

### 页面模式

| 模式 | 触发 | 功能 |
|------|------|------|
| `create` | `?action=create` | 创建审核申请（模板或自由流程） |
| `view` | `?action=view&id=xxx` | 查看、审批、编辑、撤回 |

### 审批工作流

1. `getSubmissionDetail` → submission + steps + files + signatures + 角色标志
2. 构建 `flowTimeline`（按 round 分组）— ⚠️ 此逻辑在 submissionDetail.js **内部**实现，与 venue 的 `utils/flowTimeline.js` 独立
3. 两种审批路径：弹窗审批 / 内联审批（主 UX 路径）

### 审批步骤卡展开规范

审批步骤卡展开详情必须位于同一 `.flow-info` 卡片内部，并在该可视卡片上显式添加 `.flow-info-expanded`；禁止只依赖祖先状态类和 CSS 顺序。展开态必须稳定覆盖已通过绿色或驳回红色背景并切换为白色玻璃层。`.flow-expand-detail` 与 `.flow-detail-processed-*`、`.flow-detail-comment` 只在 `subpackages/main/styles/home.wxss` 维护，场地借用详情必须复用该层级与样式；修改后验收通过/驳回的收起和展开四种状态。

### 审核模板卡操作规范

- 模板摘要和展开入口位于第一行；编辑、删除使用共享 `.card-actions` 独立操作行；展开步骤内容位于操作行之后。
- 编辑、删除按钮复用人事成员卡片的小操作样式，危险操作保持红色语义。禁止通过 `position:absolute`、固定 `top/right` 或负 margin 与展开按钮争抢卡片头部空间。
- 模板卡修改后必须在手机、Pad 竖屏、Pad 横屏分别验收长模板名、编辑/删除换行、收起和展开状态。

### 模板审批人重新指定契约

- 模板修改时，只能在模板明确允许的情况下显示第一步“指定/修改指定”入口；服务端必须再次校验第一步开关、组织范围和模板原始审批条件。
- 第一步指定入口必须位于第一步模板预览卡内部；选择器的最小选项和气泡均为“人员 · 岗位”，同一自然人的不同岗位必须分开选择。请求同时携带 `personHrIds` 与对应的 `assignmentIds`，禁止只绑定自然人。已指定人员岗位在该卡内以紧凑气泡展示，禁止另起独立的第一步审批人卡片，未允许指定时不显示入口。
- 驳回后重提交创建新轮次时，模板步骤必须从模板原始条件重建，不能沿用上一轮已经收窄的指定人员条件；这样每个审批人重新收到某一步时，仍能按该步骤原始候选范围重新指定下一步。
- 审批页只在“下一步允许指定”时显示人员选择器；未开启时不显示入口，服务端也必须拒绝携带的指定人员参数。
- 人员选择器使用审批专用候选人接口，不调用管理员专用 `listHrInfo`；前端按部门、身份类别和职能组筛选当前组织、当前步骤原始条件返回的岗位候选集合。
- 全局卡片式选择统一为整卡点击：`.selection-option-card` 自身绑定选择事件，选中时使用科技蓝边框与淡蓝背景包住整张卡；再次点击取消。禁止独立“选择/已选/取消”椭圆控件、姓氏圆形头像或把选中状态拼入信息气泡。人员候选区与已选区同样执行，正文保持 `flex:1; min-width:0`。批量目录保留独立查看/编辑入口，其事件必须隔离，不能同时触发选中。此规则取代旧版左上选择控件规则。
- 已选岗位不得使用整行“移除”操作；卡片正文必须可收缩但不能被选择控件或 `width:100%` 操作条挤成逐字窄列。修改后必须验证手机、Pad 竖屏、Pad 横屏的长姓名、多岗位、选择/取消与滚动到底。

### Round 和 Resubmit

| 模式 | 行为 |
|------|------|
| `fresh` | 从第 1 步重新开始 |
| `from_rejector` | 从驳回步骤继续 |

**Step 状态：** `pending` → `approved` / `rejected` / `superseded`（新 round 覆盖）

### 签名定位系统

**Snapshot-undo：** 打开定位时存 `_placementSnapshot`；取消时恢复；确认时丢弃。

## 3. signaturePad 组件 — 视口绝对坐标契约

签名板固定使用普通视图实时笔迹，原生 Canvas 只负责隐藏导出：

1. 可视白板为普通 `view`，实时线段也为普通 `view`；可视原生 Canvas 属于硬性违规。
2. 白板 rect、`Touch.clientX/clientY` 和线段端点统一为视口 CSS px（逻辑像素）绝对坐标。线段事实数据保存 `screenX1/Y1/screenX2/Y2`，禁止 scrollTop、DPR、rpx 或固定偏移。
3. 白板完成布局、尺寸变化或弹窗重新显示后重新测量 rect；普通视图渲染时才根据当前 rect 从绝对端点减一次 `left/top`，不得把旧 rect 推导的局部坐标写入事实数据。白板与笔迹层必须裁切。
4. 隐藏 Canvas 不绑定触摸，只在确认时将绝对端点投影到白板局部坐标并导出 1:1 PNG；导出 buffer 按白板实际可视宽高统一取整，禁止 DPR 放大。
5. 严格 UI 审计必须检查上述结构；改动后必须用真实鼠标/触控事件验证，禁止直接调用组件方法生成验收线。

## 4. 通知系统

7 种通知类型（`pending_approval`、`submission_approved/rejected/progress`、`booking_approved/rejected` 等）。
持久通知保留 30 天；待办由当前业务状态实时计算，旧 `pending_approval` 通知不进入通知列表。批量创建上限 200 条。

- 跨组织消息可以汇总，但每一条必须绑定服务端确认过的组织与可用工作角色；跳转前先切换到该组织/岗位，目标详情仍须独立做资源授权，可信路径白名单不能替代业务权限。
- 通知只能在白名单目标页成功建立后提交已读；导航失败、角色不符或服务端写入失败都保持未读。跨组织/岗位跳转使用绑定通知、组织、工作角色和目标路由的短时一次性内存回执，过期立即失效，不得用长期缓存补记已读。
- 已读、单条删除、全部已读和全部清除只作用于当前消息范围。全部清除不得删除实时待办；跨组织批量操作必须返回失败组织，前端遇到部分成功时回读服务端事实，不能保留乐观结果。
- 通知发件箱和最终通知都按“组织 + 业务事件 + 收件人”幂等。损坏载荷、非法收件人或投递失败必须重试/进入死信，禁止生成空通知后标记完成。
- 单条操作在任一候选工作角色查询失败且没有找到确定目标时，必须返回暂时失败，不能把不完整查询误报为不存在。

## 5. 审核文件、签名与验签访问

- 文件读取、预览和下载共用同一授权函数：先校验当前组织，再校验管理员细权限，或校验提交岗位、当前待审批岗位、本人历史处理岗位、明确验签授权。岗位历史缺少不可变引用时失败关闭。
- 授权成功后仍必须校验磁盘路径位于审核附件根目录，并核对数据库记录的文件大小和 SHA-256；路径越界、文件缺失或内容漂移不得下发、预览或下载。
- 签名模板只允许当前组织、当前在职岗位所属成员读写；保存的手写签名必须是受支持的图片 Data URL，并实施字符数、解码大小和图片类型上限。签名模板删除不得改写历史签名记录。
- 验签只在当前组织中匹配文件和审核记录；普通成员必须有当前组织验签授权，管理员必须有 `audit.verification`。文件内容、文件哈希和记录 ID 必须同时校验格式与大小，不能用异常输入触发无界解码或全库查询。
- 文件/签名底层异常只写内部日志，用户只收到 locale 中的自然语言失败提示；不得返回磁盘路径、PDF 解析器、数据库或加密库错误。

## 8. 当前岗位与历史快照

- 模板发起条件、审批候选、指定审批人、待办和审批动作全部基于有效组织成员岗位。身份类别只是岗位的一个字典维度，不能当作工作上下文或岗位 ID。
- 执行动作时只认当前工作上下文中的 `assignmentId`；候选阶段符合条件不代表之后仍可审批，服务端必须按当前岗位再次核验。无岗位成员不得发起或处理岗位规则驱动流程。
- 模板或上一审批人指定具体人员时，条件必须同时保存自然人/成员引用与 `assignmentId`；执行时两者必须同时匹配。禁止指定一个人后允许其任意岗位处理。
- 旧模板的人员条件若能唯一映射到一个在职岗位可以迁移；无法唯一映射时必须停用模板并要求管理员复核，禁止按自然人或当前岗位回退放行。
- `audit_flow_template_step_conditions.specific_department_id/specific_identity_id/specific_work_group_id` 是逗号分隔的 OR 集合，不是单值外键。保存和删除字典时必须在组织锁内拆分逐项校验；禁止把整串 ID 直接 JOIN、误判为孤儿或为该列建立标量外键。历史 `step_conditions_json` 保持不可变。
- 发起、每轮步骤创建和每次处理都必须保存不可变的组织、`contextId`、`assignmentId`、岗位性质、部门、身份类别和职能组快照。历史详情只展示当时快照，不用当前人事资料覆盖。
- 旧步骤缺失岗位快照时只允许展示明确标记的历史资料，不得据此授予待办或详情访问；禁止用 `hr_info`、当前岗位或自然人相同作为授权兜底。
- 跨组织待办可以全局汇总展示，但执行前必须进入指定组织并切换到满足原规则的岗位；错误组织或错误岗位必须拒绝。
- 审核提交、轮次、步骤、文件签名和岗位快照是不可变历史。编辑已驳回/已撤回申请只能新建修订数据或新轮次，禁止物理删除旧步骤和签名；状态检查必须放入与修改相同的事务和行锁中。
- 待审核申请重新提交时，旧待处理步骤标记为 `superseded` 后必须按模板原始条件创建新轮次和新的首个 `pending` 步骤，禁止出现申请为待审核但没有待处理步骤。
- 详情读取和预览不得写数据库、重建签名链或根据当前模板覆盖历史；历史信息缺失时明确提示并失败关闭。

## 9. 模块特定禁止事项

- ❌ 修改 submissionDetail 不测试创建和审批两条完整路径
- ❌ 改动 signaturePad 不测试开发者工具模拟器和实际触控设备
- ❌ 审批流程中跳过 EventBus `approval:done` 事件
- ❌ 签名定位弹窗取消后不恢复 `_placementSnapshot`
- ❌ 审批后忘记 `markSubmissionRead`
- 审批人员选择统一复用共享组件；以 `assignmentId` 选中，一岗一卡、同岗位元组筛选；整卡科技蓝选中，不保留姓氏圆圈与独立勾选。
